# Round 1 - EDI/CEDI vs SPI6 Analysis

## 목적

- 요청을 실행 가능한 연구 과업으로 재정의한다.
- 세 관점의 서브에이전트 의견을 모아 round-1 수준의 합의안을 만든다.
- 합의가 부족하면 round-2에서 좁혀야 할 쟁점을 확정한다.

## 이번 라운드의 공통 입력

- 논문 발췌:
  - `docs/papers/Objective_Quantification_extracted.txt`
  - `docs/papers/Kim2009_CEDI_extracted.txt`
- 코드:
  - `pipeline/edi_algorithm.py`

- 산출물:
  - `outputs/final_figure_data_gangneung_105_2010-2025.csv`
  - `outputs/final_figure_data_seoul_108_2010-2025.csv`
  - `outputs/final_figure_data_gwangju_156_2010-2025.csv`

## 메인 에이전트의 초기 사실 정리

- 현재 저장소에는 EDI, CEDI, SPI6 비교용 코드가 이미 존재한다.
- 다만 "논문 기반 재구현"과 "실제 가뭄 탐지 검증"이 한 문서 안에서 명시적으로 닫혀 있지는 않다.
- 산출물 극값상 핵심 사례 후보는 서울/광주 2022년, 강릉 2015-2016년이다.
- 따라서 이번 과업은 "코드 작성"만이 아니라 "논문 정의, 구현, 실험, 사례 검증, 설명 문서"를 하나로 묶는 일이다.

## 서브에이전트 의견

### 1. LLM 관점

- 최종 산출물은 단순 구현 코드가 아니라, EDI/CEDI/SPI6를 동일 기준으로 비교하고 실제 가뭄 사건 탐지력을 검증하는 재현 가능한 분석 패키지여야 한다.
- 가장 큰 모호성은 "3개 알고리즘"의 범위, 정량 평가 지표의 유무, baseline과 결측 처리 규칙, 실제 가뭄 라벨의 정의다.
- 필수 성공기준으로는 동일 날짜축과 baseline, 지점별 비교 그래프/CSV, 실제 사건과의 탐지 시점 비교, heavy-rain 이후 CEDI의 장점 확인, SPI6와 EDI/CEDI의 시간척도 차이 설명이 제시되었다.
- 한 줄 권고: 비교 기준을 먼저 잠그고 그 규칙으로 세 지표를 다시 돌려야 한다.

### 2. 소프트웨어 아키텍트 관점

- 핵심 계산 코드는 이미 존재하지만, `run_longterm_cedi_pit.py`에 알고리즘/실험/시각화가 결합되어 있어 재현성과 실험 스펙 관리가 약하다.
- 현재 SPI6 구현은 표준 정의와 완전히 동일하다고 보기 어려우므로, 이번 과업에서 어떤 SPI6를 채택하는지 명시해야 한다.
- 기존 시계열 CSV만으로는 이벤트 라벨, hit/miss, lead/lag, false alarm 같은 검증 지표를 판단할 수 없다.
- 권장 구조는 토론 로그와 별도의 실험 스펙 문서를 두고, 산출물은 `series.csv`, `metrics.csv`, `event_windows.csv`, `manifest.json`, plot 세트로 관리하는 것이다.
- 한 줄 권고: 알고리즘을 더 늘리지 말고 이벤트 기반 검증 하네스를 먼저 고정하라.

### 3. 엔드유저 관점

- 사용자가 기대하는 것은 "누가 더 좋은 지수인가"를 한눈에 보여주는 동일 형식의 3지점 비교 결과와, 실제 가뭄 사건과의 대조 설명이다.
- 현재 신뢰를 깎는 요소는 deliverable 범위 불명확, 사건별 탐지 해설 부재, 지표별 최저 시점 차이에 대한 설명 부족, 논문 이론과 구현 차이의 연결 부족이다.
- 사용자는 이벤트 타임라인, heavy-rain 이후 과대평가 보정 사례, 장기/단기 시간척도 차이, 지역별 일관성과 차이, 오경보/미탐 요약표를 꼭 보고 싶어 한다.
- 한 줄 권고: 알고리즘 비교보다 사건 단위 검증표와 해설을 먼저 완성해야 한다.

## 메인 에이전트 종합

- 세 관점은 모두 "구현 완료"보다 "비교 스펙과 사건 기반 검증 기준 확정"이 선행되어야 한다는 데 합의했다.
- 현재 저장소는 완전한 백지가 아니라 EDI/CEDI/SPI6 계산과 일부 산출물이 이미 있는 상태이므로, round-2의 목표는 새 알고리즘을 늘리는 것이 아니라 비교 스펙을 잠그는 일이다.
- 서울/광주 2022년, 강릉 2015-2016년은 현재 산출물 극값상 핵심 사례 후보이며, round-2에서 사건 윈도우 형식과 지표를 고정해야 한다.

## 잠정 합의

1. 이번 과업의 중심은 "세 알고리즘을 구현했다"가 아니라 "세 알고리즘을 같은 기준으로 비교하고 실제 가뭄 사건과 대조해 검증했다"이다.
2. round-2에서 반드시 고정할 항목은 알고리즘 범위, baseline, 실험 기간, 사건 윈도우 정의, 평가 지표, 산출물 구조다.
3. 합의가 끝나면 원본 문서에 실험 스펙을 반영하고, 그 다음 메인 에이전트가 구현/검증 단계로 넘어간다.

## 남은 쟁점

- "3개 알고리즘"을 EDI/CEDI/SPI6로 확정할지 여부
- SPI6 정의를 현재 구현대로 둘지, 표준형으로 다시 맞출지 여부
- 실제 가뭄 사건의 기준 자료와 윈도우 단위를 어떻게 고정할지
- 최종 deliverable을 어디까지 공식 결과물로 볼지
